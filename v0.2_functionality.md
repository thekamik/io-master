# IO Master v0.2: architecture and functionality

This document records what version 0.2 of IO Master is and what it can do. It is the inventory for the new Rust project: every capability listed here is either carried over, changed on purpose, or dropped on purpose.

| | |
|---|---|
| Source | commit `6cc4091` (branches `v0.2`, `V0.2`, `v0.3`; same tree as `origin/main`) |
| Language | C17, built with CMake |
| Size | about 18 000 lines of C in 60 files (`src/`, `include/`) |
| Platform | Linux only |
| State | builds without warnings; both end-to-end test suites pass (checked 2026-10-14) |
| Documentation | `README.md` (usage), `docs/architecture.md` (structure and the Common Criteria design) |

---

## 1. Purpose

IO Master is a command-line tool for investigating IoT and OT devices. During v0.2 its aim moved from a "serial reader" towards a **framework for AI-assisted Common Criteria evaluation**:

- **Device investigation** (implemented): discover a device, talk to it over UART or Bluetooth, keep what was observed.
- **Common Criteria evaluation support** (designed, not implemented): help the evaluator work through the work units of the CEM, with every decision and every command on a device left to the evaluator. The design is Part 2 of `docs/architecture.md`.

## 2. Architecture

### 2.1 Layers

```text
main.c ─ command line (cli/) ─┬─ projects (project/) ─ storage (storage/)
                              │        │
                              │   protocol registry (protocol/)
                              │        ├─ uart/        termios, udev
                              │        ├─ bluetooth/   BlueZ over D-Bus
                              │        └─ ai/          chat shell
                              │                │
                              └─ ai-config ────┴─ AI module (ai/)
                                                  HTTPS (libcurl), keyring (libsecret)
```

| Layer | Path | Lines | Responsibility |
|---|---|---:|---|
| Entry point | `src/main.c` | 78 | Parse, prepare storage, dispatch |
| Command line | `src/cli/` | 2 094 | Option parser, the commands, the `ai-config` questions |
| Projects | `src/project/` | 784 | Project list, selection, settings paths |
| Storage | `src/storage/` | 415 | Location of `im_config`, atomic JSON files |
| Discovery | `src/discovery/` | 443 | Serial devices from the udev database |
| Protocol registry | `src/protocol/protocol.c` | 137 | Table of `protocol_t`: `init`, `print_help`, `run` |
| UART | `src/protocol/uart/` | 1 573 | Serial port access and the UART shell |
| Bluetooth | `src/protocol/bluetooth/` | 6 450 | BlueZ access, scan table, connect, pair, agent, shell |
| AI shell | `src/protocol/ai/` | 1 361 | Chat menu and chat |
| AI module | `src/ai/` | 4 628 | Providers, HTTPS, keyring, AI settings, saved chats |

### 2.2 Extension points

Two registries; adding an entry adds a capability without changing the callers.

| Registry | Interface | Table | Entries in v0.2 |
|---|---|---|---|
| Protocols | `protocol_t` (`include/protocol/protocol.h`) | `src/protocol/protocol.c` | `uart`, `bluetooth`, `ai` |
| AI providers | `ai_provider_t` (`include/ai/provider.h`) | `src/ai/ai.c` | `anthropic`, `gemini` |

### 2.3 External dependencies

| Library | Used for |
|---|---|
| libsystemd: sd-device | Enumerating serial devices from the udev database |
| libsystemd: sd-bus | BlueZ (cards, devices, discovery, pairing agent); the Secret Service through libsecret |
| jansson | All JSON files and the JSON of the AI services |
| libcurl | HTTPS requests to the AI services |
| libsecret | API keys in the keyring of the system |

### 2.4 Stored data

Everything lives in `im_config/`, **next to the executable** (resolved from `/proc/self/exe`).

| File | Content | Written by |
|---|---|---|
| `project_config.json` | Projects and the selected project | project commands |
| `projects/<id>.json` | Settings of one project; content defined by its protocol | `project add`, the shells |
| `ai/ai_config.json` | AI provider, model, limits, *name* of the keyring entry | `ai-config` |
| `ai/chats/<project id>/<chat id>.json` | One saved chat (transcript and provider state) | AI shell |
| `ai/chats/<project id>/index.json` | `{"next_id": N}`, so ids of deleted chats are never reused | AI shell |

All JSON files are written to `<file>.tmp` and renamed, so a file is never left half-written. Files are indented by four spaces, so they can be edited by hand. A repeated key in an object is rejected when reading. A project listed without its settings file is reported as **damaged** and cannot be selected or run. An `ai_config.json` found at the old place (`im_config/ai_config.json`) is moved to `im_config/ai/`.

### 2.5 Cross-cutting behaviour

- **Ctrl+C** never ends a shell. It stops the current operation (reading, scanning, connecting, waiting for an AI reply) and returns to the prompt. Implemented with a `SIGINT` handler without `SA_RESTART` and a flag that every loop checks.
- **Errors** are reported where they happen, in plain sentences on standard error; functions return `0` / `-1` with `errno`.
- **Shells** are line-based: prompt, one line, parse with a table-driven parser, execute. Each shell has its own parser; the line-reading code is duplicated between the shells.

### 3.4 UART protocol

Settings (`projects/<id>.json`): `device` (empty at first), `baudrate` (9600, 19200, 38400, 57600, 115200), `data_bits` (5–8), `parity` (`none`/`even`/`odd`), `stop_bits` (1/2). Default 9600 8N1. Every value is validated when the shell starts.

| ID | Function | Details | Status |
|---|---|---|---|
| UART-1 | Shell | Prompt `uart> `; lines up to 255 characters; Ctrl+D or `exit` leaves | done |
| UART-2 | Startup | Without a port: shows the device list. With a port: connects and reports a missing permission or device without closing | done |
| UART-3 | `scan` | The device table (DSC-1) | done |
| UART-4 | `select PORT` | Checks that the path is a character device, stores it, closes the old connection, connects | done |
| UART-5 | `permission` | Runs `sudo chmod a+rw -- PORT` directly (no shell), in the same terminal; reports when access already exists | done |
| UART-6 | `read` | Raw mode, settings applied, pending data discarded on open; prints received bytes until Ctrl+C; detects an unplugged device | done |
| UART-7 | Connection | Opened `O_NONBLOCK`, `O_NOCTTY`; waits with `pselect` with `SIGINT` blocked outside the wait (no lost Ctrl+C) | done |

Not available: **writing to the port**, timestamps, hex view, capture to a file, other baud rates, a non-interactive interface.

### 3.7 Common Criteria evaluation support

Designed only (`docs/architecture.md`, Part 2). Nothing is implemented. The design defines:

- **Principles P1–P5**: the evaluator decides; no command reaches a device without an action of the evaluator for that command; everything is traceable; the norm is data (replaceable CC/CEM index files); the model reads documents but does not search the norm.
- **Two pipelines** per work unit: *conceptual* (assessed from documents, returns cited passages and a PASS/FAIL estimate) and *functional* (adds a test plan, approval, guided execution and a test report).
- **Components**: norm index, document library, quote verification, test plan (JSON + text, frozen by checksum), guided execution, action layer (closed list: `open`, `send`, `receive`, `expect`, `close`), report writer.
- **Data formats** (sketches): evidence, conceptual result, test plan, execution log; storage under `im_config/norms/` and `im_config/evaluations/<project id>/`.
- **Roadmap**: foundations (UART send, action layer, machine interface, structured AI answers, Bluetooth data), then stages A–E.
- **Open decisions** D1–D4: first norm version, document formats, need for a local model, language of the assistant.

## 5. Known limits of the v0.2 structure

These come from `docs/architecture.md` and from the code. They are the reasons a restructuring is needed for the Common Criteria direction.

1. **Protocol logic lives inside the interactive shells.** There is no way for another part of the program to say "send these bytes and give me the answer". The planned action layer and guided execution need exactly that.
2. **UART is read-only**, and Bluetooth exchanges no data with a device.
3. **The AI module returns text only**; the pipelines need structured answers.
4. **No machine interface**: everything is meant for a person at a terminal.
5. **Configuration is tied to the location of the executable** (`im_config` next to it).
6. **Code is duplicated** between the shells (line reading, Ctrl+C handling), and each shell has its own parser.
7. **Fixed-size buffers and limits** everywhere (names, paths, 32 serial devices, 256 projects and Bluetooth devices).
8. **No logging or event record** of what was done on a device; the only records are the AI chats.
9. **Tests cover only the Bluetooth and AI shells**, end to end.
